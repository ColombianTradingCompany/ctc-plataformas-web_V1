4 · Seguridad

Alta SEG-1 · La vista ai_usage_resumen es legible por Internet anónimo

migración ai_usage_resumen_view (2026-08-10) · lint security_definer_view (nivel ERROR)

La vista del libro de consumo de IA se creó SECURITY DEFINER y con GRANT por defecto a anon/authenticated. La tabla base ai_usage está bien cerrada (RLS deny-all, service-role), pero la vista la salta. Confirmado en vivo con la clave anon:

GET /rest/v1/ai_usage_resumen?select=*  → HTTP 200
[{"dia":"2026-08-10","proveedor":"anthropic","modelo":"claude-sonnet-5",
  "superficie":"direccionamiento","llamadas":4,"fallidas":1,
  "costo_usd":0.090976}, {"superficie":"gvg:match", ...}]

Un desconocido puede leer, día a día, cuánta IA gasta CTC, con qué modelos, en qué superficies (incluida gvg:match, el espacio personal del owner) y el costo en USD. No es PII ni credenciales — es inteligencia operativa que no debería ser pública. Es exactamente el patrón que V14 aceptó a propósito para public_lot_catalog, pero aquí no hay razón de negocio para exponerlo: la vista solo la consume el tablero interno /ecp/consumo.

Corrección. REVOKE ALL ON public.ai_usage_resumen FROM anon, authenticated; (el tablero del ECP lee con service-role, así que no se rompe nada). Opcionalmente recrearla como security_invoker=on. Es una migración de una línea y es la prioridad #1 de seguridad.

Alta SEG-2 · bajarFeed es una primitiva SSRF sin compuerta

src/lib/coffeed/feedActions.ts:163

Todo export de un módulo "use server" es un endpoint POST invocable por cualquier cliente, tenga o no la UI un botón para él. bajarFeed acepta una URL arbitraria, hace fetch(url, {redirect:"follow"}) y devuelve el cuerpo — sin studioGate(), sin allowlist de host, sin bloqueo de IP privada. Su hermana resolverFeeds (mismo archivo) sí llama al gate; ésta no.

export async function bajarFeed(feedUrl: string): Promise<string | null> {
  return bajar(feedUrl, 20_000);  // fetch(url,{redirect:"follow"}) → devuelve res.text()
}

Sirve como proxy abierto y para alcanzar servicios internos (localhost, endpoints de metadatos) y leer la respuesta. En Vercel serverless no hay el IMDS clásico de EC2, así que el impacto es menor que en una VM, pero sigue siendo una SSRF real que devuelve cuerpo a un anónimo. Su único uso legítimo es interno, desde el barrido ya gated (aiActions.ts).

Corrección. No exportarla desde el módulo "use server": renombrar a bajar (helper interno) y que el barrido la importe como función normal, no como acción. Si debe ser acción, envolver con studioGate() + allowlist de esquema/host + redirect:"manual".

Media SEG-3 · membresiasDe/puedeSer revelan la membresía de cualquier usuario sin sesión

src/lib/identidad/matriz.ts:30 y :63

Ambas son acciones "use server" que aceptan un profileId arbitrario y, con el cliente service-role, devuelven si esa identidad es productor / comprador-real / directorio / recolector / socio / admin (consultando orders, lot_reservations, buyer_profiles). No hay verificación de sesión. Las variantes correctas para superficies públicas son las de sesión (puedoSer, misPlataformasRed), que sacan el id del usuario logueado. Mitigante real: el profileId es un UUID (no enumerable a ciegas) y la salida son booleanos, no PII.

Corrección. Dejar exportadas solo las variantes de sesión; convertir membresiasDe/puedeSer en helpers server-only (el único llamador legítimo, terratalento/actions.ts, ya pasa user.id).

Baja SEG-4 · Higiene menor de funciones (regresiones pequeñas vs. V14)

  • quotes_assign_code con search_path mutable (nueva, de ocp_cotizador_quotes). No es SECURITY DEFINER, así que el riesgo es el mismo bajo que tenían las 4 de V14 antes del fix; fijar a public, pg_temp por consistencia.
  • producer_owns_comm(uuid,uuid) ejecutable por anon — es la función SECURITY DEFINER que rompió el bucle de recursión RLS (gotcha 11b). Devuelve un booleano, utilizable como oráculo de "¿existe esta nota?"; riesgo bajo, pero authenticated la necesita y anon no — revocar de anon.
  • Las 17 funciones de trigger siguen expuestas por RPC (lints 0028/0029). Aceptado igual que en V14 (SEC-3): Postgres las rechaza en compilación con "trigger functions can only be called as triggers"; explotabilidad nula. Sin cambio.

5 · Estabilidad y resiliencia

Alta EST-1 · El envío del OTP del panel no comprueba su resultado

src/lib/bcp/sendOtpEmail.ts:22 · src/app/api/panel/auth/password/route.ts

resend.emails.send() devuelve {error} sin lanzar, y aquí se descarta con un await pelado. Si Resend falla, la ruta responde {ok:true}, el usuario espera un código que nunca llega, y cada reintento quema uno de los 3 códigos por ventana de 15 min. Con el historial de fallos de login del BCP, es un modo de fallo invisible que puede bloquear la única puerta del panel. Es el único sender del sistema que no persiste su resultado — todos los demás (invite_email_error, welcome_error, notificacion_error) sí lo hacen.

Corrección. Que sendOtpEmail devuelva el SendResult; la ruta responde error (y compensa el slot de rate-limit) cuando el envío falla. Envolver el send() para que un throw de red no escape del try/catch de la ruta.

Alta EST-2 · Un adjunto que falla al subir se pierde para siempre, en silencio

src/lib/buzon/syncBuzon.ts:136-145

El módulo del Buzón declara como regla #1 "NEVER lose mail". Se cumple para el cuerpo, no para los adjuntos: la subida a Storage hace if (!upErr) attachmentsMeta.push(...) — si falla, no hay retry, no se anota nada en la fila, y el insert del correo procede igual. Como el dedupe es por message_id, ese mensaje nunca se re-importa; y la limpieza de retención (30 días) borra el original de Hostinger porque la fila SÍ quedó archivada. Una factura PDF puede desaparecer sin rastro.

const { error: upErr } = await service.storage.from(BUCKET).upload(path, att.content, ...);
if (!upErr) { attachmentsMeta.push({...}); }   // si falla: se ignora y el correo entra igual
Corrección. Si algún upload falla, abortar el insert de ESE mensaje (queda sin fila → se reintenta en el próximo run, que es idempotente), o registrar attachment_error en la fila y excluir ese message_id del cleanup de retención.

Media–Alta EST-3 · Cuatro acciones de IA pueden dar un 504 mudo al superar los 300 s

datawaveActions.ts:144 · rtScriptorActions.ts:718 · gvg/matchActions.ts:325 · (patrón)

La lección del 2026-08-05 (el fetch de Node corta a los 300 s y Vercel mata la función a los maxDuration=300) no se aplicó de forma uniforme en las apps nuevas. Cuando la función muere a mitad, el catch de la acción nunca corre, así que ni se ve el mensaje amable ni se limpia el estado — la fila queda clavada.

AcciónPeor casoConsecuencia
buildEpisode (Datawave)240 s + reintento de timeout olvidado = 483 s > 300504 mudo; el catch no corre
renderTake (RT-Scriptor)hasta 8 fotogramas × 120 s sin techo de sumacoffeed_rts_renders.state='rendering' eterno

Corrección. buildEpisode: añadir timeoutRetries:0. renderTake: presupuesto de tiempo por trabajo (si Date.now()-t0 > 200s, cerrar los restantes con error) o bajar el timeout por imagen a ~45 s. runGvgMatch/next-step/mejoras/ticker: AbortSignal.timeout() por debajo del maxDuration para que el catch existente haga su trabajo.

Media EST-4 · Dos carreras de useAutosave que reportan "Guardado ✓" sin guardar

src/lib/useAutosave.tsx:87 · src/components/kaffetal-regal/InfoModal.tsx:70

La corrupción original de useAutosave (leer refs del DOM que React ya soltó, gotcha 10b) está bien resuelta — todos los consumidores son estado controlado. Pero quedan dos carreras más suaves:

  • Cambio durante un guardado en vuelo (useAutosave.tsx:87): si el save A tarda >3,5 s (cold start) y llega un cambio B, el timer de B dispara con savingRef===true y hace return sin re-agendar; el efecto solo se relanza al cambiar serialized, así que B queda sin persistir mientras el chip dice "guardado". Se pierde si el usuario cierra la pestaña.
  • InfoModal no espera su guardado (:70): save({silent:true}); return true; sin await — reporta éxito aunque el write falle y permite dos writes solapados de la misma fila.
Corrección. Al terminar el vuelo, comparar el snapshot vigente contra el último guardado y re-agendar si difieren; en InfoModal, return await onSave(...).

Media ESTR-3 · El proxy fuga contenido por comparar con startsWith, y no hay robots.txt/canonical en subdominios

src/proxy.ts:78 y :162 · sin sitemap.ts · sin metadataBase

  • Fuga de host: como /cherry-picked es prefijo de /cherry-picked-green|roast|x, el host del hub sirve las tres superficies hermanas con 200 — incluido el callback OAuth de Green funcionando en el host equivocado. La UI nunca genera esos enlaces (FAMILY_LINKS es absoluto en prod), así que el daño es contenido duplicado + un bucle de OAuth si se teclea la URL. Arreglo de una línea: comparar por frontera de segmento (pathname===base || pathname.startsWith(base+"/")).
  • robots.txt da 404 en los 18 subdominios — el matcher no lo excluye, así que el proxy lo reescribe a una ruta inexistente. Los crawlers lo leen como "permitir todo". Hoy no expone nada sensible (las consolas llevan noindex de respaldo y viven en www, donde el disallow sí aplica), pero es higiene SEO rota. Añadir robots.txt (y sitemap.xml) a las exclusiones del matcher.
  • Sin canonicals: cada superficie es alcanzable en 2-3 URLs (www/base, sub/, sub/base) sin alternates.canonical. Sitio B2B de tráfico bajo → señal repartida, no penalización. Un canonical estático por superficie lo cierra.
  • Footgun latente: el lookahead del matcher (api|_next|images|docs|tools) no está acotado por /, así que una ruta futura como /toolshed o /apis escaparía del proxy en silencio. Acotar con /.

8 · Revisados y aceptados (sin cambio, con motivo)

Aceptado A-1 · 63 tablas con RLS activo y sin políticas

Es el modelo deny-all salvo service-role del sistema, por diseño (Arena, leads, coffeed_*, gvg_*, terratalento_*, directorio_*, panel_users…). Verificado en vivo: GET /rest/v1/ai_usage y /rest/v1/leads con la clave anon devuelven []. RLS activo sin políticas ES la denegación. No es un hallazgo (salvo la vista ai_usage_resumen que lo salta — SEG-1).

Aceptado A-2 · Las 2 vistas de catálogo público (public_lot_catalog, public_transparency_pricing)

SECURITY DEFINER a propósito, proyección estrecha y curada — reconfirmado. No exponen ficha ni geolocalización. Igual que V14.

Aceptado A-3 · Los 14 triggers guarda, la cookie de panel y la hidratación jsonb

Los 14 triggers guarda (funciones guard_*/coffeed_guard_*) están todos atados a su tabla y coinciden con el modelo documentado. Ninguna acción de panel lee la cookie compartida ni viceversa (el patrón dual de studioGate es deliberado). La hidratación jsonb (hydrateDoc, toLabEvaluationList, EMPTY_FICHA, Datawave) protege filas viejas — solo run_state queda fuera (EST-6). El contrato never-throw del correo se cumple en 6 de 7 senders (la excepción es EST-1).

9 · Higiene de BD diferida (deliberadamente NO aplicada)

Un linter no conoce la escala. Igual que en V14, estas recomendaciones automáticas se rechazan por ahora:

  • 83 claves foráneas sin índice — correcto en abstracto, prematuro con ~1.200 filas totales (la mayor tabla, 306). Umbral de revisión: cuando cualquier tabla pase de ~10.000 filas, priorizando las FK que se usan en JOIN/filtro (lots.finca_id, arena_inscriptions.lot_id, producer_comm_log.lot_id).
  • 9 índices "sin uso" — aparecen sin uso porque la base es joven, no porque sobren; borrarlos ahora es tocar tablas en transición (club, quotes, directorio, rts, ai_usage) por nada.
  • Storage a ~550 MB de 1 GB, con buzon/ en 144 MB (295 archivos) y sin poda automática. La retención de 30 días del Buzón solo borra de Hostinger, no de Storage. No urgente, pero el bucket es finito — anotar una poda de adjuntos del Buzón cuando pase de ~800 MB.
  • Crons de Vercel: 2 de 2 usados (Hobby). No queda slot para un tercer cron; cualquier tarea periódica nueva tiene que colgarse de after() o de uno de los dos sweeps existentes.

10 · Lo que NO se encontró

Acota el alcance de lo revisado:

  • Ninguna ruta de escritura sin autenticar en las consolas: cada Server Action reautentica; ningún formulario inline depende solo del gate del layout; ningún componente "use client" importa supabase/server ni server-only.
  • Ninguna política RLS sin envolver auth.*() (0 de 54) — la corrección estrella de V14 aguantó 40 migraciones.
  • Ninguna fuga de datos entre productores/compradores; el scoping de ownership en clientes de sesión es consistente (nadie hace update/delete por id sin filtro de propiedad; RLS es el backstop).
  • Ningún secreto en el cliente; service_role solo en createServiceRoleClient(), siempre en servidor.
  • Higiene de logs limpia: 3 console.log en todo src/ (los tres fallbacks de dev sin RESEND_API_KEY).
  • tsc y next build limpios; las 98 rutas compilan.

11 · Acción pendiente del owner

Bloqueado por plan Protección de contraseñas filtradas

Sigue deshabilitada, como en V14, y sigue bloqueada tras el plan Pro (la organización está en Free). Supabase → Authentication → Providers → Email. Mientras tanto, sin costo, se puede subir la longitud mínima (≥12) y exigir tipos de carácter — no depende del plan. El panel además exige 2FA por OTP.
